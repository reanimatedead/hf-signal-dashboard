## 規則

1. 実物を叩いていない識別子を書かない
2. 検証コマンドが誤合格しない形か（`test -f` → `grep -c`、`|| echo OK` 禁止）
3. 完了条件が依頼の言葉を直接測っているか
4. 制約が物理か選択かを区別しているか
5. 動いているものを退行させていないか
6. 会話内で自分が述べた制約と矛盾していないか
7. 修正パッチの波及先を洗ったか

### 規則8: 観測した状態を不変条件としてテストに固定しない

- **発生した誤り**: n_0dte_contracts=0 を見て「0DTEは常に捕捉不能」と断定した。実際は引け後スナップショット限定の現象で、ライブ取得中は捕捉可能だった。
- **検査**: 一度の観測が「常にそうである」ことを意味するか検討したか。条件によって変わりうるなら条件分岐としてテストを書いたか。

### 規則9: 同一の指標に複数の閾値を置かない

- **発生した誤り**: contract test 95% と health_gate 90% を別々に指定し、厳しい方が先に落ちる構造を作った。19銘柄の一時劣化で契約スイート全体が落ちた。
- **検査**: 同じ指標を複数箇所で判定していないか。役割（量の判定=ゲート / 質の判定=契約テスト）で置き場所を決めたか。
